Chapter 01 // Definition

📖 What is WordPress?

WordPress is an open-source content management system (CMS) written in PHP and backed by MySQL/MariaDB. It lets anyone — from bloggers to Fortune 500 companies — build and manage a website without writing code. And it powers 43% of all websites on the internet.

📝 The LEGO analogy

Think of WordPress core like a LEGO baseplate. By itself, it's a solid rectangle — functional but boring.

Themes are the colors and shapes of your bricks — they change how it looks.

Plugins are the motorized kits, the lights, the moving parts. They add contact forms, SEO tools, e-commerce, sliders, caching, analytics… anything you can imagine.

Here's the catch: LEGO quality-controls their official kits. WordPress does NOT quality-control plugins. Anyone can publish a plugin. Many are abandoned, unpatched, and full of vulnerabilities. That's why 97% of WP vulnerabilities come from plugins.

Chapter 02 // Architecture

🏗️ The four layers of WordPress

🧱 Core

The WordPress application itself — PHP files that handle routing, the admin panel, the editor, user management, the REST API. Maintained by Automattic + the open-source community. Gets automatic security patches. Relatively hardened — only ~3% of WP vulns are in core.

🎨 Themes

PHP/CSS/JS templates that control the visual layout. Stored in /wp-content/themes/. Some themes are just CSS; others contain complex PHP logic (page builders, AJAX handlers) — and that logic can be vulnerable.

🔌 Plugins

Extensions that add functionality. Stored in /wp-content/plugins/. This is where 97% of vulnerabilities live. Third-party devs, varied quality, often abandoned after a few updates. Every plugin is a separate attack surface.

🗄️ Database

MySQL/MariaDB stores posts, users, passwords (phpass hashed), settings, and plugin data. Default table prefix: wp_. Connection credentials live in wp-config.php.

Typical WordPress file structure

/var/www/html/ ├── wp-config.php # 🔑 DB creds, auth keys, salts — THE target ├── wp-login.php # Login page — brute-force target ├── xmlrpc.php # Legacy API — brute-force amplifier ├── wp-settings.php # Bootstrap file ├── wp-cron.php # Scheduled tasks ├── wp-admin/ # Admin dashboard │ ├── admin-ajax.php # AJAX handler (plugin vulns often here) │ └── ... ├── wp-includes/ # Core libraries │ └── ... └── wp-content/ # 🎯 User-generated content ├── themes/ # Active + inactive themes ├── plugins/ # 🔥 97% of vulns live HERE │ ├── contact-form-7/ │ ├── elementor/ │ └── ... └── uploads/ # Media library (check for PHP shells) └── 2026/05/

Chapter 03 // Why it's target #1

💥 Why pentesters and bug hunters obsess over WordPress

43%

Massive attack surface

43% of ALL websites = hundreds of millions of installations. Find one plugin vuln → it affects millions of sites simultaneously. That's scale that makes researchers drool.

60,000+

Plugin explosion

60,000+ plugins on wordpress.org alone, plus thousands more sold on CodeCanyon and other marketplaces. Each one is a separate PHP codebase you can audit. Most have zero security review.

97%

Plugins = 97% of vulns

WP core gets patched fast and auto-updates. Plugins? Many are one-person side projects. Developer ghosts the plugin after v1.2, and 200K installs sit there, unpatched, waiting for a CVE.

Recon gold

Predictable structure

Every WP site has the same file paths: /wp-admin/, /wp-login.php, /xmlrpc.php, /wp-json/. Tools like WPScan exploit this predictability to enumerate everything.

⚠️ Real numbers: In 2023 alone, Wordfence reported 4,528 new WordPress vulnerabilities. That's 12+ new WP vulns per day. The vast majority were in plugins. If you're looking for bugs to hunt, WordPress is a target-rich environment.

Chapter 04 // The pentester's hit list

🎯 Where to probe on any WordPress site

  • /wp-login.php — Login form. Brute force with Hydra, WPScan, or Burp Intruder. Check for username enumeration via error messages.
  • /xmlrpc.php — XML-RPC endpoint. Multicall brute-force amplification, pingback SSRF, DDoS reflection. Should be disabled; rarely is.
  • /wp-json/wp/v2/users — REST API user enumeration. Often returns usernames in JSON even if registration is closed.
  • /wp-content/plugins/ — Directory listing? Reveals installed plugins. Even without listing, probe known plugin paths for readme.txt files that leak version numbers.
  • /wp-content/uploads/ — Media uploads. Check for directory listing → find uploaded files. Sometimes attackers upload PHP shells disguised as images.
  • /wp-config.php backup files — Hunt for .bak, .old, .save, .swp, ~ extensions. wp-config.php backups served as plain text = database credentials on a silver platter.
  • /?author=1 — User enumeration via author archive redirect. Reveals the username for user ID 1 (usually admin).
🧠 Brain Power
WordPress core accounts for only ~3% of all WP vulnerabilities. Plugins account for ~97%. Why are plugins SO much more vulnerable than core?

Third-party code, varied quality, and abandonment.

WordPress core is maintained by a dedicated security team at Automattic, gets automatic updates, and has been audited extensively. Plugins, on the other hand, are written by anyone — a freelancer, a student, a company that pivoted away.

Many plugins:

  • Have no security review before being published to wordpress.org
  • Are maintained by a single developer who may abandon the project
  • Don't implement basics like input sanitization, nonce checks, or capability verification
  • Have auto-update lag — even when a patch is released, site owners often don't update for weeks or months

The result: a never-ending supply of vulnerable code sitting on millions of live websites.

Chapter 05 // Real-world breaches

📰 When WordPress plugins get people pwned

2024 / CVE-2024-27956

WP-Automatic — SQLi to admin

A critical SQL injection in the WP-Automatic plugin let unauthenticated attackers create admin accounts, upload backdoors, and take full control. Over 30,000 sites used this plugin. Exploit was in the wild within days of disclosure.

2021 / CVE-2021-24507

Flavor — Stored XSS (100K+ installs)

The flavor theme allowed unauthenticated stored XSS. Attackers injected JavaScript that ran in admin browsers, enabling session hijacking and full site takeover on 100,000+ installations.

2020 / CVE-2020-35489

Contact Form 7 — file upload RCE

The world's most popular WP plugin (5M+ installs) had an unrestricted file upload vulnerability. Attackers uploaded PHP shells through the contact form. One plugin. Five million sites at risk.

2019 — Panama Papers trail

Mossack Fonseca — unpatched Revolution Slider

The law firm behind the Panama Papers leak ran WordPress with an unpatched Revolution Slider plugin (known vuln since 2014). Attackers walked in through a 3-year-old plugin vuln. 11.5 million documents leaked. 2.6 TB. World-shaking scandal — and it started with a WordPress plugin.

Chapter 06 // Hardening WordPress

🛡️ How to make WordPress less of a sitting duck

  • Keep everything updated — Core, themes, AND plugins. Enable auto-updates for minor releases. Check weekly for plugin patches.
  • Delete unused plugins + themes — Deactivated ≠ safe. The PHP files are still on disk and reachable. Delete what you don't use.
  • Disable XML-RPC — Unless you specifically need it (Jetpack, mobile app). Block at the web server level or use a security plugin.
  • Hide version info — Remove the WordPress version meta tag. Change the default wp_ table prefix. Don't make recon easy.
  • Restrict /wp-admin/ access — IP whitelist or VPN for the admin panel. Add 2FA to admin accounts.
  • Protect wp-config.php — Move it one directory above the web root (WP supports this). Block access via .htaccess rules. Never leave backups in the web root.
  • Web Application Firewall — Wordfence, Sucuri, or Cloudflare WAF to catch common exploit patterns before they reach your plugins.
  • Audit plugins before installing — Check last-updated date, active installs, support forum activity. If it hasn't been updated in 2+ years, walk away.

A WordPress site has 15 plugins installed but only 5 are active. The other 10 are deactivated. Are the deactivated plugins still a security risk?
