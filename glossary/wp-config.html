Chapter 01 // Definition

📖 What is wp-config.php?

wp-config.php is the main configuration file for WordPress. It lives in the web root (or one directory above it) and contains everything WordPress needs to connect to its database and run securely — credentials, cryptographic keys, table prefix, debug settings, and custom constants.

📝 The master keyring analogy

Imagine a janitor's master keyring — one ring that holds the key to every door in the building: the vault, the server room, the CEO's office, the alarm system panel.

Now imagine someone leaves a photocopy of that keyring in the lobby, labeled "BACKUP — DO NOT USE."

That's what happens when a wp-config.php backup file ends up in the web root. The web server doesn't execute .bak or .old files as PHP — it serves them as plain text. Anyone who requests it gets database credentials, auth salts, and the keys to every lock in the kingdom.

why pentesters hunt it
Chapter 03 // The hunt

💥 Why wp-config.php is a pentest goldmine

🗄️ Database credentials

The DB_USER + DB_PASSWORD + DB_HOST combo. If the database is exposed (bad firewall rules, port 3306 open), you connect directly and dump everything — users, hashed passwords, posts, settings.

🔐 Auth keys + salts

With the cryptographic salts, an attacker can forge valid WordPress session cookies for any user — including admin. No password needed. Just cookie crafting.

🔁 Password reuse

The DB password is often reused for SSH, FTP, admin panel logins, or other services. One credential leak → lateral movement across the entire infrastructure.

🐛 Debug mode intel

If WP_DEBUG is true, error messages leak internal file paths, SQL query structures, and stack traces. WP_DEBUG_LOG = true writes it all to /wp-content/debug.log — another file to grab.

How backup files end up in the web root

Developers and sysadmins create backup copies of wp-config.php before making changes. Common patterns:

  • cp wp-config.php wp-config.php.bak — manual backup
  • Text editors auto-save: wp-config.php.save, wp-config.php.swp, wp-config.php~
  • Version control artifacts: wp-config.php.old, wp-config.php.orig
  • Deployment tools leaving: wp-config.php.dist, wp-config.txt

The web server (Apache/Nginx) only executes .php files as PHP. Everything else? Served as plain text. Request /wp-config.php.bak and you get the raw PHP source code — including every credential.

🎯 The backup-hunting curl loop

#!/bin/bash # Hunt for wp-config.php backup files # Run this against authorized targets ONLY TARGET="https://target.com" EXTENSIONS=("bak" "old" "save" "orig" "copy" "tmp" "txt" "swp" "swo" "~" "1" "2" "backup" "dist" "inc" "php.bak" "php.old" "php~") for ext in "${EXTENSIONS[@]}"; do url="${TARGET}/wp-config.${ext}" code=$(curl -s -o /dev/null -w "%{http_code}" "$url") if [ "$code" == "200" ]; then echo "[!] FOUND: $url (HTTP $code)" fi done # Also check common alternate filenames for name in "wp-config-backup.php" "wp-config-sample.php" \ "config.php.bak" ".wp-config.php.swp"; do url="${TARGET}/${name}" code=$(curl -s -o /dev/null -w "%{http_code}" "$url") if [ "$code" == "200" ]; then echo "[!] FOUND: $url (HTTP $code)" fi done

what to do with it
Chapter 05 // Post-discovery

🔓 You found wp-config.php — now what?

1️⃣ Try the DB creds on MySQL

If port 3306 is open: mysql -h target -u wp_admin -p. Dump wp_users table, grab password hashes, crack them offline with hashcat.

2️⃣ Try creds on wp-login.php

Password reuse is king. Try the DB password as the WordPress admin password. You'd be surprised how often it works.

3️⃣ Try creds on SSH / FTP

Same password on SSH? Game over — you have a shell. Same on FTP? Upload a PHP webshell. Password reuse is the gift that keeps on giving.

4️⃣ Forge auth cookies

With the AUTH_KEY, SECURE_AUTH_KEY, LOGGED_IN_KEY, and their salts, you can craft valid session cookies for any WordPress user without knowing their password.

5️⃣ Check for debug.log

If WP_DEBUG_LOG is true, fetch /wp-content/debug.log. It often contains SQL errors (leak table structure), file paths, PHP warnings, and sometimes even credentials passed through deprecated functions.

6️⃣ Note the table prefix

If it's not the default wp_, you'll need the custom prefix for any SQL injection payloads: SELECT * FROM custom_users instead of wp_users.

🧠 Brain Power
You found wp-config.php.bak and got DB credentials. The database isn't exposed to the internet (port 3306 is closed). Is the wp-config.php leak still useful?

YES — absolutely. The database not being internet-facing doesn't make the leak useless. Here's why:

  • Password reuse is extremely common. Try the DB password on: wp-login.php, SSH (port 22), FTP (port 21), cPanel, PHPMyAdmin, any other admin panels on the same server.
  • Auth keys + salts let you forge admin session cookies — no database access needed.
  • Debug mode info (if WP_DEBUG = true) tells you internal paths and PHP version — useful for further exploitation.
  • The DB_HOST value might reveal internal infrastructure: a hostname like db.internal.company.com or an internal IP like 10.0.1.50 — recon gold for further SSRF or pivoting.
  • If you later get a shell (via any other vector), you can connect to the DB from the server itself using mysql -h localhost with the creds you already have.

Bottom line: A wp-config.php leak is ALWAYS valuable, regardless of whether the database is directly reachable.

defense
Chapter 06 // Protecting wp-config.php

🛡️ Lock it down

  • Move it up one directory — WordPress natively supports loading wp-config.php from one directory above the web root. This puts it outside the publicly accessible path entirely.
  • Block access via .htaccess:
# Deny all access to wp-config.php <Files wp-config.php> Order Allow,Deny Deny from all </Files>
  • Never leave backups in the web root — after editing, immediately delete any .bak, .old, .swp, or ~ files. Better yet, edit on a local machine and deploy via git.
  • Set restrictive file permissions — chmod 400 wp-config.php (read-only, owner only). The web server user needs read access; nobody needs write.
  • Use unique, random salts — Generate from https://api.wordpress.org/secret-key/1.1/salt/. Never use the default placeholder strings.
  • Rotate DB credentials — if you suspect any leak, change the password immediately. Also rotate auth salts to invalidate all existing sessions.
  • Disable WP_DEBUG in production — define('WP_DEBUG', false). Error messages in production = information disclosure.

Chapter 07 // Real-world examples

📰 When wp-config.php leaks go wrong

Bug bounty classic

The .bak file that paid $5,000

A researcher on HackerOne found wp-config.php.bak on a Fortune 500 company's marketing subdomain. The DB password was reused on the staging server's admin panel. Full admin access. P1 severity. $5,000 bounty for a single curl request.

Common in CTFs

Every WordPress CTF box ever

WordPress-themed CTF boxes (THM, HTB) almost always include a wp-config.php discovery step. Find the backup → get creds → use them somewhere else (SSH, admin panel). It's THE archetypal WP recon finding.

Vim swap files

The .swp that nobody cleaned up

Vim creates .wp-config.php.swp when you edit a file and don't close cleanly. It's a hidden file (starts with dot), but web servers still serve it at /.wp-config.php.swp. Use vim -r .wp-config.php.swp to recover the original file contents including all credentials.

2019

Mossack Fonseca (Panama Papers)

The law firm behind the Panama Papers leak had a WordPress site with known vulnerabilities AND exposed configuration. Poor WP hygiene was part of the attack chain that led to the biggest document leak in history — 11.5 million files, 2.6 TB of data.
