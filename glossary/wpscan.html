Chapter 01 // Definition

📖 What is WPScan?

WPScan is a free, open-source, black-box WordPress vulnerability scanner. It probes a WordPress site from the outside — enumerating installed plugins, themes, and users, checking their versions against a massive vulnerability database (WPVulnDB), and optionally brute-forcing credentials.

📝 The building inspector analogy

Imagine hiring an inspector to walk around the outside of a building. They don't go inside — they just look at what's visible: the locks on the doors, the brand of windows, whether there's a fire escape, the sign out front listing the company name.

Then they pull up a database: "That lock model was recalled in 2023 — it can be picked with a bobby pin." "That window brand has a known bypass." "The fire escape ladder is missing rungs."

WPScan is that inspector, but for WordPress sites. It fingerprints what's installed, then checks if any of it has known vulnerabilities. All from the outside.

Chapter 02 // Getting started

⚡ Installation — three ways

💎 Ruby gem (native)

gem install wpscan

Needs Ruby 2.7+ and development headers. Best for Kali/Parrot where deps are pre-installed.

🐳 Docker (cleanest)

docker pull wpscanteam/wpscan docker run -it --rm \ wpscanteam/wpscan \ --url target.com

Zero dependency headaches. Works anywhere Docker runs.

🐧 Kali/Parrot

# Already pre-installed! wpscan --version

Both major pentesting distros ship WPScan out of the box.

💡 API token: WPScan's vulnerability database requires a free API token for full vuln data. Sign up at wpscan.com, grab your token, and pass it with --api-token YOUR_TOKEN. Without it, you still get enumeration — but no CVE details.

Chapter 03 // Essential commands

🛠️ The 5 most useful WPScan commands

# 1. Full recon — enumerate vulnerable plugins, themes, and users wpscan --url https://target.com \ --enumerate vp,vt,u \ --api-token YOUR_TOKEN # 2. Aggressive plugin detection (finds plugins passive mode misses) wpscan --url https://target.com \ --enumerate ap \ --plugins-detection aggressive # 3. Brute-force wp-login.php with a wordlist wpscan --url https://target.com \ -U admin \ -P /usr/share/wordlists/rockyou.txt # 4. Brute-force via XML-RPC (faster, often bypasses rate limits) wpscan --url https://target.com \ -U admin \ -P passwords.txt \ --password-attack xmlrpc # 5. Stealthy scan (random user-agent, throttled requests) wpscan --url https://target.com \ --enumerate vp,vt,u \ --random-user-agent \ --throttle 500

Enumeration flags cheat sheet

Chapter 04 // Reading the output

📊 Interpreting WPScan results like a pro

WPScan uses a color-coded system in the terminal. Here's what matters:

🟢 [+] Interesting findings

Detected WordPress version, server headers, interesting HTTP headers, exposed readme files. Not vulns on their own, but pieces of the puzzle.

🟡 [!] Warnings

Outdated plugin/theme versions, detected XML-RPC, missing security headers. These need attention — they're often exploitable.

🔴 [!!] Vulnerabilities

Known CVEs matched against detected versions. This is the money. Each one includes: CVE ID, vuln type (SQLi, XSS, RCE…), affected versions, references. Start here.

📋 Users enumerated

Usernames found via author archives, /?author=N, and REST API. These become the -U list for brute-force attacks.

🧠 Brain Power
WPScan says "No plugins found." Does that mean the site has no plugins?

No! It means passive/default mode didn't find any.

WPScan's default --plugins-detection mixed mode checks a curated list of ~2,000 popular plugins by probing known paths. If a plugin isn't in that list (or its files are hidden behind a WAF), it won't show up.

Switch to --plugins-detection aggressive and WPScan will test against a database of 100,000+ plugin slugs. It's slower (and noisier — the target WILL see it in logs), but it catches what passive mode misses.

Takeaway: "No plugins found" in passive mode just means the scan was too quiet. Crank it up before concluding the site is plugin-free.

real world
Chapter 05 // Real-world impact

📰 WPScan in the wild

Bug bounty staple

First tool in WP recon

On platforms like HackerOne and Bugcrowd, when a target runs WordPress, WPScan is the first thing every researcher runs. It's practically step 0 of WP-focused bug bounty methodology. Many critical findings start with wpscan --enumerate vp.

CTF / THM / HTB

Standard for WP-based boxes

Every WordPress-themed CTF box or TryHackMe room expects you to use WPScan. The enumeration output gives you the plugin version, you search the CVE, and you have your initial foothold. It's that formulaic.

⚠️ Legal note: WPScan, like any scanner, should only be run against targets you own or have explicit authorization to test. Unauthorized scanning is illegal under CFAA and similar laws worldwide. Stick to CTFs, bug bounty programs in scope, and your own test environments.
